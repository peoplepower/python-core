# When to use

Any time you (human or agent) want to capture durable knowledge — a system, a dataset, an API, a
metric, a process, a runbook.

# Steps

1. Pick or create a subdirectory that groups the concept sensibly
   (e.g. `apis/`, `services/`, `playbooks/`).
2. Create `<concept>.md` with frontmatter. Only `type` is required; `title` and `description` are
   strongly recommended, because `description` is what the generated index files display.

   ```markdown
   ---
   type: API Endpoint
   title: Create Order
   description: POST endpoint that places a customer order.
   resource: https://api.example.com/v1/orders
   tags: [orders, api]
   status: stable                       # draft | stable | deprecated
   generated: { by: claude/opus-5, at: 2026-09-08T00:00:00Z }
   verified:
     - { by: human:your-id, at: 2026-09-08T00:00:00Z }
   stale_after: 2027-03-08T00:00:00Z
   sources:
     - id: order-service
       resource: example-org/order-service:src/orders
       title: Order service implementation
       last_modified: 2026-08-30T00:00:00Z
   ---

   # Examples
   ...
   ```

3. Cross-link related concepts with bundle-relative links, e.g. `[the spec](/SPEC.md)`. Links to
   not-yet-written concepts are fine — they mark what is worth writing next. A link to a concept in
   a *different* bundle must be fully qualified as `bundle://<name>/<path>`, resolved through the
   registry at `~/.okf/registry.md` (override with `OKF_REGISTRY`) — `okf.py validate` checks these
   and warns on unregistered names or missing targets.
4. Add a dated entry to the [update log](/log.md), newest first. Date headings must be bare ISO dates
   (`## 2026-09-08`); a parenthetical suffix fails validation.
5. Regenerate indexes and validate:

   ```sh
   python3 tools/okf.py index
   python3 tools/okf.py validate
   ```

6. Commit. The bundle is git-distributed, so history and attribution come for free.

# The v0.2 frontmatter families

| Family | Fields | Purpose |
|---|---|---|
| Identity | `type` (required), `title`, `description`, `resource`, `tags` | What this is |
| Provenance | `sources` | Where the content came from |
| Trust | `generated: { by, at }`, `verified: [{ by, at }]` | Who produced and confirmed it |
| Lifecycle | `status`, `stale_after` | Whether it can still be relied on |

## Actors

Three forms identify who did something:

* `<producer>/<version>` for agents — `claude/opus-5`
* `human:<id>` for people — `human:your-id`
* `process:<id>` for automated processes — `process:nightly-sync`

The `human:` prefix is load-bearing: it is what raises a concept's trust tier. A concept with no
`verified` key is **unverified**; verified only by non-human actors it is **machine-confirmed**;
verified by a `human:` actor it is **human-reviewed**.

## Per-claim attribution

Attribute individual claims with markdown footnotes whose label is a `sources[].id`, not a position.
This document's own frontmatter declares `id: spec`, so a claim sourced to it is written:

> Only `type` is a required frontmatter field. [^spec]

and the footnote definition at the bottom of the body carries the human-readable label.

`okf.py validate` warns when a footnote label matches no `sources[].id` — which catches attribution
that has drifted away from its source list, and which it will do to this very sentence if the `spec`
entry above is ever renamed.

# Conventions

* Prefer structural markdown (tables, lists, fenced code) over prose.
* Use the conventional headings `# Schema`, `# Examples`, `# Computation` where they apply (see [SPEC.md](/SPEC.md) §4.2).
* Reserved filenames `index.md` and `log.md` must never be used for concepts. Index files are generated by `okf.py index` — do not hand-edit them. The one exception is the bundle-root `index.md`, which carries hand-authored frontmatter (including `okf_version`) and is skipped by the generator.
* **Record corrections rather than silently overwriting.** When a figure is superseded, update the concept *and* append a `**Correction**:` entry to [log.md](/log.md) saying what was wrong and why. The trail is what makes the current numbers trustworthy.

# Changed from v0.1

Both legacy forms are still honored by the tooling, so old concepts keep working — but new ones should
use the v0.2 fields.

| v0.1 | v0.2 |
|---|---|
| `timestamp: <iso>` | `generated: { by: <actor>, at: <iso> }` |
| `ttl_days: 180` | `stale_after: <absolute iso datetime>` |
| a body `# Citations` list | the `sources` frontmatter family |

`stale_after` is deliberately absolute rather than a relative TTL: a date does not silently change
meaning when a document is copied, and it is unambiguous to a reader who has no access to the tooling.
See [Keeping knowledge fresh](/playbooks/keeping-knowledge-fresh.md).
